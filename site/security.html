Security model

Error correction is not security

AUDP-ECM protects data against accidental damage: noise, interference, fading and dropped bytes. It does not protect against a deliberate attacker. Both matter, and they need different tools.

What it does and does not protect against

ThreatAUDP-ECMWhat you need
Random noise, interference, fading✔ corrected up to capacity, detected beyond it—
Bursts of lost or garbled bytes✔ corrected up to depth·t with burst framing—
Deliberate modification of a frame✘ an attacker can craft valid codewords and CRCsMAC (e.g. HMAC-SHA-256) or AEAD
Forged frames from an impostor✘Authentication: MAC/AEAD with per-device keys, or signatures
Replay of old frames✘Sequence numbers or nonces inside the authenticated data
Eavesdropping✘Encryption: AEAD such as AES-GCM or ChaCha20-Poly1305
Jamming / denial of servicepartial: tolerates noise up to capacityPhysical-layer and network measures

A CRC is not a MAC. CRC-16 and Reed–Solomon parity are public, linear functions. Anyone can recompute them after changing the data, so a matching CRC proves only the absence of accidental errors.

Recommended layering

  1. Sender: encrypt and authenticate the payload with an AEAD (or append a MAC). Include a sequence number.
  2. Then protect the authenticated bytes with AUDP-ECM (error correction is the outermost layer on the link).
  3. Receiver: decode with AUDP-ECM first. If that fails, drop the frame or request a retransmission.
  4. Then verify and decrypt with the AEAD. Reject the frame if authentication fails, or if the sequence number repeats.

This order lets error correction repair channel damage before the authentication check, which would otherwise reject every frame with a single flipped bit.

How the library itself is hardened

  • Memory-safe implementation. The bindings forbid unsafe code (Python) or expose only @safe APIs (D).
  • Every input is validated, and failures raise typed errors. Malformed input never crashes or corrupts memory.
  • Decoded data is verified before it is returned. Burst frames add a CRC-16 as a second check.
  • Bounded resource use: input sizes, interleave depth and erasure lists are capped.
  • Fuzzing, property-based tests and memory-safety checking in continuous integration. Dependencies are audited.
  • Release artifacts carry SHA-256 checksums and signed build-provenance attestations.
